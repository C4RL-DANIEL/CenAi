AGENT SAFETY

Designing approval-first AI agents

A practical safety pattern for AI agents: separate reading from acting, use least privilege, preview changes, require confirmation and keep a recovery path.

By CenAIUpdated 17 November 20268 min read
In this guide
  • Separate action levels
  • Apply least privilege
  • Make approvals meaningful
  • Treat external content as untrusted
  • Plan for failure

Separate reading, preparing and acting

An AI agent is more than a chat response when it can call tools, edit files, send messages or interact with accounts. The important design question is not only whether the model can complete a task. It is what the system is allowed to change while trying.

A useful starting point is to divide work into three levels:

  • Read: inspect permitted information, search documents, summarize records or check a status.
  • Prepare: draft a message, propose a code patch, create a plan or assemble a change preview without committing it.
  • Act: publish, send, purchase, delete, grant access, modify production data or trigger an external workflow.

Reading can often happen with limited permissions. Preparing should preserve a clear draft or diff. Acting should require a stronger authorization path when the result is consequential.

Apply least privilege to every tool

Give an agent only the permissions needed for its current task. A research agent may need read-only access to selected documents, not permission to send email or change billing. A code agent may work in a branch or sandbox rather than pushing directly to the production branch. A calendar assistant may draft an event before it receives permission to invite other people.

Permissions should be scoped by user, resource, action and time where possible. Avoid one broad token that grants every capability. Prefer short-lived credentials, explicit revocation and server-side checks. A model's statement that a user approved an action is not proof of authorization; the application should verify approval through its own trusted state.

Make approvals meaningful

A confirmation dialog is useful only if it tells the user what will happen. Before approval, show the target system, account, recipient, amount, files or records affected, and whether the action can be undone. If the agent changes its plan after approval, require approval again for the changed action.

Use clear choices such as “Approve once”, “Edit draft”, “Reject” and “Stop task”. Do not hide a consequential action inside a generic “Continue” button. Approval should be tied to a specific action summary, not to an entire open-ended conversation.

Example: sending an email

The agent can read the selected brief and draft a message. Before sending, show the recipient, subject and full message body. If the recipient or body changes after review, ask again. Record whether the user approved, edited or rejected the send operation.

Treat external content as untrusted input

Documents, web pages, emails and code repositories can contain instructions that try to override the user's intent. A page might tell an agent to reveal secrets, upload files or ignore its safety rules. The agent should treat this material as data to analyze, not as a source of new authority.

Keep system policy and user authorization separate from retrieved content. Restrict tool arguments, validate outputs, avoid exposing secrets to the model, and require confirmation before sending data outside the trusted workspace. This is commonly discussed as prompt injection and is covered in the OWASP Top 10 for Large Language Model Applications.

Plan for failure and recovery

Agents can time out, call the wrong tool, receive partial responses or lose network connectivity. Design operations to be observable and, where possible, idempotent. Keep a record of the task, tool, inputs, result, approval and timestamp. For changes to files or data, preserve a diff, version or backup. For external actions, show whether the provider confirmed success instead of assuming that a button click means the action completed.

Provide a stop control that prevents new actions and define how an in-progress operation is handled. A stop button cannot always undo an email already sent or a payment already captured, so explain the limits honestly.

Test the boundaries, not only the happy path

Test a normal task, a missing permission, a malicious document, a changed recipient, a repeated request, a network failure and a user rejection. Confirm that the agent pauses at the correct point, does not reuse stale approval and does not claim success when a tool reports failure. Review logs for sensitive data and avoid storing more than the task requires.

Key takeaway

Safe autonomy is built through architecture, not reassuring language. Separate read and write permissions, scope credentials, make approvals specific, treat retrieved content as untrusted and preserve an auditable recovery path.
