SECURITY & TRUST

Security is a
system property.

These are the security requirements for CenAI. This document describes intended controls, not a certification or a claim that every control is already deployed.

Release integrity

Protected signing credentials, signed APKs, checksums, provenance, dependency scanning, and channel-aware update verification.

Least privilege

Minimal Android permissions, scoped integrations, explicit user consent, and no hidden root or accessibility bypasses.

Backend security

Server-side authorization, short-lived tokens, rate limits, secret rotation, input validation, and environment separation.

AI guardrails

Tool allowlists, prompt-injection defenses, data boundaries, bounded execution, spend limits, and human approval.

Privacy

Data minimization, encrypted transport and storage, user export/deletion, and no conversation-content telemetry by default.

Quality gates

Automated tests, real-device validation, API authorization tests, recovery drills, and independent review before major releases.

Threat model priorities

  1. Credential theft, API abuse, and exposed signing material.
  2. Repackaged APKs, tampered updates, and fraudulent releases.
  3. Cross-user data access, insecure project isolation, and session compromise.
  4. Prompt injection, malicious documents, and unauthorized tool execution.
  5. Supply-chain compromise, dependency vulnerabilities, and unsafe CI permissions.
  6. Telemetry overcollection, backup exposure, and unintended data retention.

CenAI cannot make a distributed APK impossible to reverse-engineer. The architecture must assume client binaries can be inspected and keep secrets and critical authorization decisions on trusted servers.
